# План завершения Artfolio MVP

Актуальная версия плана развития проекта. Этот документ фиксирует согласованный объём первого MVP и критерии его готовности.

## Цель MVP

Публичное портфолио художницы Анны Аветисян и закрытая административная панель, через которую автор самостоятельно управляет профилем, социальными ссылками и работами.

Главный визуальный акцент сайта — произведения. Аватар автора в MVP не используется и не входит в модель продукта.

## 1. Завершить функциональность

### Рефакторинг REST API перед новыми функциями

Перейти от отдельного контроллера для каждой функциональной области к одному контроллеру на версию REST API. Выполнить рефакторинг до реализации социальных ссылок, пока изменение маршрутов и структуры относительно дешёво.

Целевая структура:

```text
internal/controller/restapi/
├── middleware/
├── router.go
├── server.go
└── v1/
    ├── controller.go
    ├── router.go
    ├── error.go
    ├── session.go
    ├── artist_profile.go
    ├── artwork.go
    ├── social_link.go
    ├── request/
    └── response/
```

Правила структуры:

- Один `Controller` содержит зависимости всех use case одной версии REST API.
- Методы контроллера разделяются по предметным файлам, а не по отдельным пакетам и типам.
- `request` и `response` содержат транспортные DTO и не смешиваются с бизнес-сущностями.
- Верхний `restapi/router.go` подключает версию API, а `v1/router.go` регистрирует её маршруты.
- Middleware остаются вне версионного контроллера, если применяются ко всему REST API.
- Другие транспорты, включая будущий Kafka consumer, получают собственные контроллеры и не добавляются в REST `Controller`.
- Добавить версию в публичные маршруты: `/api/v1/...`.
- Обновить обращения frontend к API одновременно с переносом маршрутов.
- Не менять поведение endpoint во время структурного рефакторинга.
- Подтвердить эквивалентность поведения существующими unit- и integration-тестами.

### Социальные сети

- Добавить отдельную таблицу `artist_social_links`.
- Поддержать фиксированный набор площадок для MVP: Telegram, Instagram, VK и Behance.
- Хранить тип площадки и её уникальную часть (`handle`), а не полный URL.
- Строить полный URL на backend по доверенному шаблону выбранной площадки.
- Реализовать repository, use case и REST API.
- В админке показывать конкретный набор полей для поддерживаемых площадок, а не форму произвольной ссылки.
- Принимать как handle, так и вставленный полный URL или значение с `@`, нормализуя ввод до handle.
- Не создавать или удалять запись при очистке соответствующего поля.
- Возвращать вместе с публичным профилем только заполненные социальные ссылки.
- Никогда не возвращать и не отображать пустую площадку, например Instagram без аккаунта.
- Выводить в разделе контактов только фактически заполненные ссылки.
- Автоматически адаптировать раскладку списка контактов под количество доступных ссылок на мобильных и десктопных экранах.
- Убрать временные отдельные поля `telegram` и `instagram` из frontend-модели в пользу универсального списка ссылок.
- Валидировать `platform`, формат handle и допустимую длину значения отдельно для каждой площадки.
- Добавить уникальность `(artist_profile_id, platform)`: у профиля может быть не больше одного аккаунта каждой поддерживаемой площадки.
- Добавить unit- и integration-тесты.

Предлагаемая структура таблицы:

```text
artist_social_links
-------------------
id
artist_profile_id
platform
handle
created_at
updated_at
```

Публичный API возвращает готовые `label` и `url`, чтобы frontend не содержал правила построения ссылок. Административный API работает с `platform` и `handle`.

Пустое значение означает, что социальная сеть не настроена и не должна отображаться. Отдельный статус публикации и ручная сортировка для MVP не требуются; порядок задаётся фиксированным списком поддерживаемых площадок.

## 3. Автоматические проверки и качество

### Учебный трек: Go concurrency

Artfolio является учебным пет-проектом, поэтому concurrency-паттерны входят в план осознанно. Они должны решать понятную задачу, поддерживать отмену через `context.Context` и не создавать бесконтрольные goroutine.

В рамках MVP не добавлять искусственную параллельность в сборку публичного профиля: ссылки запрашиваются по `artistProfileID`, полученному при чтении профиля, поэтому операции зависимы и выполняются последовательно. Продолжать проверять backend через `race detector`, поскольку HTTP-сервер конкурентен по своей природе.

После основного MVP:

- Добавить ограниченный worker pool для фоновой обработки изображений.
- Использовать buffered channel как очередь заданий и фиксированное небольшое количество workers.
- Реализовать создание уменьшенных версий и, при необходимости, конвертацию JPEG/PNG в WebP.
- Добавить backpressure: при заполненной очереди поведение должно быть определено явно.
- Реализовать graceful shutdown с прекращением приёма заданий и ожиданием активных workers через `sync.WaitGroup`.
- Обрабатывать отмену через `context.Context`, ошибки заданий и очистку частично созданных файлов.
- Не считать in-memory очередь надёжным хранилищем: отдельно решить восстановление потерянных заданий после перезапуска или периодический поиск необработанных изображений.

Обязательные проверки concurrency-кода:

- `go test -race ./...`;
- тест отмены контекста;
- тест заполненной очереди;
- тест корректной остановки workers;
- тест отсутствия зависания при ошибке одного из заданий.

## 6. Учебный этап после MVP: заявки и Kafka

Добавить в существующий frontend публичную форму заявки на приобретение работы, выставку или сотрудничество. Отдельное frontend-приложение не требуется: форма является компонентом текущего React-приложения и обращается к тому же `/api` через Caddy.

### Форма заявки

- Добавить действие «Узнать о работе» или «Оставить заявку» в карточку или подробное представление работы.
- Автоматически передавать `artworkId`, когда заявка относится к конкретной работе.
- Поддержать общую заявку без выбранной работы.
- Запрашивать имя, способ связи, тему и текст сообщения.
- Показывать состояния отправки, успеха, ошибки и возможность повторной отправки.
- Обеспечить доступность формы с клавиатуры и на мобильных устройствах.
- Не создавать отдельный frontend и не отправлять запросы напрямую в Kafka.

### Artfolio API

- Добавить `POST /contact_requests`.
- Валидировать поля, длину сообщения и существование указанной работы.
- Добавить rate limiting и базовую защиту от спама.
- Не записывать полный текст обращения и контактные данные в обычные application-логи.
- Добавить таблицы `contact_requests` и `outbox_events`.
- Записывать заявку и outbox-событие в одной транзакции PostgreSQL.
- Реализовать фоновый outbox publisher с восстановлением после перезапуска.

### Kafka

- Начать с одного основного topic `artfolio.contact-requests.v1`.
- Использовать стабильный `eventId`, `eventType`, `eventVersion`, `occurredAt` и версионируемый payload.
- Выбрать ключ сообщения так, чтобы сохранялся требуемый порядок событий одной заявки.
- Изучить partitions, offsets, consumer groups и at-least-once delivery на этом сценарии.
- После базовой доставки добавить retry topic и dead-letter topic.

### Notification Service

- Создать отдельный Go-сервис с Kafka consumer.
- Первым каналом реализовать уведомления в Telegram; email оставить дополнительным каналом.
- Сделать consumer идемпотентным по `eventId`.
- Реализовать ограниченные повторные попытки и отправку окончательно неуспешных событий в DLQ.
- Добавить health/readiness endpoint, корректную остановку consumer и базовые метрики доставки.

### Порядок изучения и реализации

1. Сделать форму в текущем frontend и временный синхронный endpoint без Kafka.
2. Сохранять заявки в PostgreSQL.
3. Поднять Kafka в локальном Compose и изучить producer/consumer на тестовом событии.
4. Добавить transactional outbox в Artfolio API.
5. Создать Notification Service и доставку в Telegram.
6. Добавить идемпотентность, retry и DLQ.
7. Добавить integration-тесты и проверить восстановление после остановки Kafka или consumer.

Такой порядок позволяет разрабатывать пользовательскую форму независимо от изучения Kafka, а затем заменить временную доставку событий надёжным асинхронным контуром.

## 7. Учебный этап после Kafka: Kubernetes

После выделения Notification Service и Kafka перенести проект с Docker Compose в Kubernetes. Для проекта это учебное усложнение, а не требование текущей нагрузки: production должен оставаться понятным в эксплуатации и укладываться в ресурсы VPS.

### Стратегия внедрения

1. Сохранить Docker Compose как простой локальный и аварийный способ запуска.
2. Поднять локальный кластер через `kind` или `k3d`.
3. Развернуть stateless-компоненты: frontend, Artfolio API и Notification Service.
4. Добавить Ingress, конфигурацию, Secrets, probes и ограничения ресурсов.
5. Запускать миграции отдельным Kubernetes Job перед обновлением API.
6. Разобраться с persistent volumes, backup и восстановлением PostgreSQL и изображений.
7. Развернуть Kafka только после проверки хранения данных и процедур восстановления.
8. Для одного небольшого VPS использовать лёгкий `k3s`, а не тяжёлый многоузловой кластер.
9. Добавить автоматизированный deployment после успешного CI.

### Kubernetes-ресурсы

- `Deployment` и `Service` для frontend.
- `Deployment` и `Service` для Artfolio API.
- `Deployment` и `Service` для Notification Service.
- `Ingress` для публичного сайта, `/api` и `/media`.
- `ConfigMap` для несекретной конфигурации.
- `Secret` для паролей БД, административных и Telegram credentials.
- `Job` для миграций.
- `PersistentVolumeClaim` для PostgreSQL и изображений.
- `StatefulSet` или подходящий оператор для stateful-компонентов, если это оправдано учебными целями.
- `NetworkPolicy`, если используемый CNI её поддерживает.

### Что изучить

- requests и limits;
- liveness, readiness и startup probes;
- rolling update и rollback;
- Jobs и init containers;
- persistent volumes и StatefulSet;
- DNS и service discovery;
- Secrets и ConfigMaps;
- Ingress и TLS;
- namespaces, service accounts и RBAC;
- Helm или Kustomize;
- базовую наблюдаемость и диагностику через events, logs и metrics.

### Ограничения и безопасность

- Не переносить PostgreSQL и Kafka в production-кластер, пока не проверены backup и restore.
- Не хранить секреты в открытом виде в Git; стандартный Kubernetes Secret — только кодирование, а не шифрование исходного файла.
- Не считать один `k3s`-узел отказоустойчивым кластером.
- Не удалять рабочий Compose deployment до успешного smoke-теста и документированного rollback.
- Не добавлять autoscaling без метрик и реальной причины.

### Критерий завершения Kubernetes-этапа

- Проект разворачивается в чистом локальном кластере одной документированной командой или короткой последовательностью команд.
- Миграции выполняются предсказуемо и не запускаются конкурентно несколькими pod.
- Rolling update не прерывает публичный сайт и корректно останавливает Kafka consumer.
- Данные PostgreSQL, изображения и Kafka-сообщения переживают перезапуск pod.
- Проверены backup, restore и rollback на предыдущую версию приложения.
- Production-развёртывание на `k3s` воспроизводимо и не зависит от ручного редактирования ресурсов в кластере.

## Критерий готовности MVP

Анна без помощи разработчика может:

- войти в закрытую админку;
- изменить профиль и контакты;
- заполнить, изменить и очистить аккаунт каждой поддерживаемой социальной сети;
- видеть на публичной странице только заполненные социальные сети без пустых элементов;
- создать, изменить, упорядочить, опубликовать, скрыть и удалить работу;
- увидеть изменения на публичном сайте;
- продолжить работу после перезапуска приложения без потери данных.

Со стороны эксплуатации:

- автоматические проверки проходят;
- production работает через HTTPS;
- существует проверенная резервная копия БД и изображений;
- основной пользовательский сценарий пройден на чистом окружении.

## После MVP

В первый MVP не входят:

- аватар или портрет автора;
- worker pool и автоматическая конвертация изображений в WebP/AVIF — они остаются обязательным учебным этапом после MVP;
- форма заявки и Notification Service через Kafka — обязательный учебный этап после базового MVP;
- Kubernetes-развёртывание — обязательный учебный этап после появления Kafka и нескольких сервисов;
- drag-and-drop сортировка;
- аналитика посещений;
- расширенное SEO;
- восстановление или ротация ключа через интерфейс;
- сложная система мониторинга и журналирования.
